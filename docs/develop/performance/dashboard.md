# Dashboard 性能优化与验证范围

反馈：Windows 桌面版打开调用记录、LLM 统计页时频繁卡顿或卡死。此前 #355 减少了 SQL 次数，但窗口函数分页仍处理全部匹配行；列表仍返回并在渲染期间解析长工具 JSON；统计和模型名称查询仍读取含大段详情的审计行。

## 实现

- 分页和计数使用独立 CTE，只在 LIMIT/OFFSET 后物化当前页 ID。计数结果左连接当前页，保证空库、筛选无结果或超出末页时仍返回正确总数，无需回退查询。页数据和总数来自同一 SQL 快照；加上全局筛选项，列表请求共两条 SQL。
- 列表只返回元数据及详情可用标志。工具定义、输出、输出工具调用和错误正文由 `/dashboard/llm-api/records/{id}/details` 按需读取，前端只解析当前打开的详情并复用缓存。输入仍使用已有 `/prompt` 接口。
- 迁移 1027 添加元数据覆盖索引和 `(model_id, model_name)` 索引。统计可以读取元数据索引而不扫描含长提示词的审计行，项目标签先去重项目 ID 再关联标题。

前后端列表字段同时变更，需要一起发布。索引增加存储和写入开销，大库首次升级需要构建索引。统计响应体没有裁剪，单条详情没有分段加载；总数和深页 OFFSET 仍有随数据量增长的开销。

## 当前验证

在工作区重新建立改动后通过 37 项后端回归测试，覆盖大详情不进入列表响应、详情读取、空页计数、所有七种排序的升降序及 NULL/同值顺序、筛选、覆盖索引执行计划和迁移升降级。后端及前端 lint/typecheck、前端构建和 Chromium 的详情缓存及六个统计图表切换检查通过。

## 历史合成基准

以下是旧工作区故障前记录的结果，未在新工作区重测。Linux、SQLite、aiosqlite，12,000 条记录、5 个模型、28 个日期，固定长度的提示词约 16 KB、工具定义/输出/工具调用各约 4 KB，数据库约 333 MB。

第一轮优化：列表加计数加筛选项约 31.69 → 10.69 ms，统计加筛选项约 95.61 → 35.99 ms，20 条列表项 JSON（不含筛选项）254,640 → 11,720 字节。预热两次后取五次中位数，原查询额外给予 `(created_at, id)` 索引。

之后在相同数据上补齐迁移 1021 的历史复合索引，两种分页方案使用相同索引，预热两次后取九次中位数：完整列表的拆分查询约 10.358 ms，CTE 约 9.487 ms。收益有限且并非所有排序更快，延迟排序约 3.441 → 3.596 ms。

这些是规则的合成数据和预热结果，不足以代表 Windows 用户的真实数据、磁盘冷读取、并发写入或 Electron 渲染压力。尚未复现 Windows 现场卡死，不能宣称所有卡死已消除；后续应使用脱敏真实库，并记录查询耗时、内存峰值及渲染主线程长任务。
